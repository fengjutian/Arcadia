# 本地知识库中文检索设计与开发文档

> 文档状态：已实现
>
> 对应数据库迁移：v27、v28、v29、v30
>
> 最后更新：2026-10-29

## 1. 目标

本功能为桌面端本地知识库提供无需联网的中英文全文检索，重点解决 SQLite FTS5 默认分词器无法可靠召回中文子串的问题。例如，文档中保存的是“南京市概况”，用户查询“南京”时也必须返回该文档。

设计目标：

- 中文单字、双字、长词和中英混合查询均可检索。
- 中文标题和标签支持全拼、拼音音节及首字母检索。
- 常用别名支持双向查询扩展。
- 标题、标签、摘要和正文使用不同权重排序。
- 标题或标签精确包含查询词时优先展示。
- 文档新增、修改标签、修改自动标签和删除后，索引保持同步。
- 老版本数据库启动后自动迁移和回填，不要求用户清空知识库。
- 所有检索均在本机 SQLite 中完成，不上传正文和查询词。

## 2. 用户流程

```text
输入查询词
  ├─ 空查询 → 按星标、创建时间返回文档
  ├─ 含 CJK 字符 → 中文混合索引（v28）
  └─ 纯拉丁文字 → 原 local_documents_fts 索引

中文检索结果
  → 精确包含层级（标题 > 标签 > 摘要 > 正文）
  → FTS5 BM25 字段权重
  → 星标
  → 创建时间
```

搜索对比页面中的“本地知识库”数据源调用同一接口，因此索引增强会同时作用于知识库页面和多数据源对比页面。

## 3. 存储结构

### 3.1 原始文档

`local_documents` 是事实数据源，保存标题、URL、摘要、Markdown 正文、标签、自动标签、星标和创建时间等字段。

### 3.2 中文混合索引

迁移 v27 创建 `local_documents_cjk_fts`：

```sql
CREATE VIRTUAL TABLE local_documents_cjk_fts USING fts5(
  document_id UNINDEXED,
  title_tokens,
  markdown_tokens,
  summary_tokens,
  tag_tokens,
  tokenize='unicode61'
);
```

`document_id` 只用于关联，不参与分词。其他字段保存应用预先生成的空格分隔词元，再交给 `unicode61` 建立倒排索引。

## 4. 中文词元策略

### 4.1 建索引

连续 CJK 文本同时生成：

- 单字：支持一个汉字的查询。
- 相邻双字：支持常见中文词和任意子串。
- 相邻三字：提高地名、机构名和较长短语的区分度。

示例：

```text
原文：南京市
索引：南 京 市 南京 京市 南京市
```

拉丁字母和数字按连续单词保留并转为小写。例如 `AI Search 2026` 生成 `ai`、`search`、`2026`。

### 4.2 查询

查询端采用更紧凑的词元集合：

- 单个 CJK 字符使用单字词元。
- 两个及以上 CJK 字符使用双字和三字词元，不再强制匹配每个单字。
- 多个词元使用 `AND` 连接，避免只因命中“市”“的”等单字而返回大量噪声。
- 双引号等 FTS5 特殊字符在生成 MATCH 表达式前转义。

示例：

```text
查询：南京城市 AI
词元：南京 京城 城市 南京城 京城市 ai
```

### 4.3 拼音与首字母

迁移 v29 为标题和标签增加拼音派生词元，正文不生成拼音，避免索引体积过度增长。例如“南京”会额外产生 `nan`、`jing`、`nanjing` 和 `nj`。纯拉丁查询先使用常规 FTS；没有结果时再查询混合索引，因此原有英文搜索和前缀匹配保持不变。

### 4.4 内置别名

迁移 v30 创建 `search_aliases` 表，设置页可以添加和删除双向别名。首次升级会预置：

- 南京 ↔ 金陵
- 人工智能 ↔ AI
- 数据库 ↔ SQLite

别名变体通过 FTS5 `OR` 合并，但每个变体内部仍使用 `AND`，在扩大召回范围的同时控制噪声。词条与别名限制为 80 个字符，重复组合由数据库唯一约束拒绝。

## 5. 排序规则

中文查询首先按字面精确包含位置分层：

1. 标题包含完整查询词。
2. 人工标签或自动标签包含完整查询词。
3. 摘要包含完整查询词。
4. 仅正文或拆分词元命中。

同一层内使用 FTS5 `bm25()` 排序，字段权重如下：

| 字段 | 权重 |
| --- | ---: |
| 标题 | 10 |
| 标签 | 8 |
| 摘要 | 4 |
| 正文 | 1 |

之后再按星标和创建时间排序。这样可以避免正文中偶然多次出现查询词的长文章压过标题精确匹配的文档。

### 5.1 高级搜索语法

搜索框支持以下离线语法，多个条件可以组合：

| 语法 | 示例 | 含义 |
| --- | --- | --- |
| 标题 | `title:南京` | 标题必须包含“南京” |
| 标签 | `tag:旅游` | 人工或自动标签必须匹配 |
| 网站 | `site:example.com` | 限定 URL 主机名 |
| 精确短语 | `"秋季旅行"` | 标题、摘要、正文或标签包含完整短语 |
| 排除词 | `-酒店` | 结果不得包含该词 |
| 日期上限 | `before:2026-10-01` | 只显示该日期之前保存的文档 |
| 日期下限 | `after:2026-01-01` | 只显示该日期之后保存的文档 |

普通关键词继续交给 SQLite 索引召回；字段、日期和排除条件由纯函数进行确定性过滤。仅包含字段条件时会读取本地文档列表后过滤。

### 5.2 搜索建议与去重

输入时最多展示 8 条建议，来源为知识库标题、标签和搜索别名；最近查询仍在空搜索框下显示。建议查询只返回短文本，不读取正文。

结果按规范化 URL 去重：忽略 URL 片段以及 `utm_*`、`spm`、`from`、`ref`、`source` 等跟踪参数。相同页面保留后端排序最靠前的结果；没有有效 URL 时使用小写标题去重。

## 6. 索引生命周期

以下操作会同步更新中文索引：

- 保存或覆盖文档。
- 修改文档字段。
- 修改人工标签。
- 修改自动标签。
- 删除文档。

索引属于可重建派生数据。v27 首次创建表并全量回填；v28 因词元算法加入三字词而再次全量回填；v29 为标题和标签写入拼音词元；v30 增加可管理别名。迁移在事务中执行，失败时不会把数据库标记为已升级。

设置页“知识库”区域显示数据库版本、文档数和已索引文档数，并提供手动重建操作。重建只删除并恢复派生索引，不删除原始文档，而且整个过程在事务中执行。

## 6.1 命中原因

后端为每条结果返回 `matchReason`：`title`、`tag`、`pinyin`、`alias`、`summary` 或 `content`。搜索结果卡片显示对应中文标签。命中原因只用于解释，不参与前端二次排序；最终相关度顺序以 Rust 查询结果为准。

大型知识库首次升级可能使启动时间增加，后续正常启动不会重复回填。

## 9. 故障排查

### 知识库中有内容但查询为空

1. 完全退出并重启桌面应用，确保 v27/v28 迁移运行。
2. 确认文档已经保存到本地知识库，而不是仅存在于网页标签中。
3. 检查数据库 `schema_version` 是否包含 27、28。
4. 检查 `local_documents_cjk_fts` 是否存在对应 `document_id`。
5. 若迁移中断，保留数据库并查看 Rust 日志；不要直接删除用户数据库。

### 首次升级启动较慢

v28 会对全部文档重新生成词元。该过程只执行一次。后续可将全量回填改为带进度的后台批处理，以优化超大型知识库体验。

## 10. 后续增强路线

按收益与复杂度建议依次实施：

1. 增加检索质量基准集和 P50/P95 性能统计。
2. 对超大型知识库采用分批回填、索引版本状态和失败续跑。
3. 引入可选中文词典分词，与 N-gram 结果合并；N-gram 继续作为无词典兜底。
4. 增加拼音/首字母字段，支持 `nanjing`、`nj` 搜索中文标题。
5. 增加同义词与别名表，例如“金陵”与“南京”。
6. 将词法结果与已有向量召回通过 RRF 融合，用于语义近似查询。

这些增强不应替换当前 N-gram 索引；后者依赖少、可解释、离线可用，适合作为稳定的基础召回层。
